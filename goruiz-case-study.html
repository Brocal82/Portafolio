Case study

Ambulancias GoRuiz

Production B2B platform for ambulance and medical transport operations — built end to end as sole developer. Private repository; screenshots and overview shared on request.

Production Private Sole developer

Context

I work as a paramedic in Berlin and built GoRuiz outside my clinical shifts. I know the domain from daily operations: shift planning, worker availability, documents, and the gap between office tools and what crews need in the field. The goal was a single system — not a demo — that admins and field staff would use every week.

Problem

  • Scheduling and worker data spread across spreadsheets, messages and ad-hoc tools
  • Office staff and field crews without a shared, up-to-date view of shifts and requests
  • Sensitive documents (contracts, certificates) needing role-based access, not public links

What I built

Admin web app

Dashboard, worker management, scheduling (Dienstplan), company settings — React + TypeScript.

Worker web portal

Browser access for staff who do not use the mobile app — same API, role-scoped data.

Field mobile app

React Native (Expo): shifts, workday, documents, messages — for crews on the road.

Shared backend

Node.js / Express REST API, MongoDB, JWT auth, multi-tenant companyId scoping.

         │                    │                    │
         └────────────────────┼────────────────────┘
                              │  REST · JWT
                    ┌─────────▼─────────┐
                    │  Node.js / Express │
                    │  MongoDB           │
                    │  Multi-tenant      │
                    └───────────────────┘

Three clients consume one API. Authentication and tenant isolation are enforced in the service layer — not only at the route — including legacy records where companyId may be null.

Key technical decisions

  • Multi-tenant from the start — each ambulance company scoped by companyId; admin operations always tenant-aware.
  • One API for web + mobile — avoids duplicate business logic and keeps mobile in sync with office tools.
  • JWT + role-based access — separate admin vs worker capabilities; documents served through authenticated routes, not public uploads.
  • i18n (DE / EN / ES) — UI and content for mixed-language teams common in Berlin operations.
  • CI with GitHub Actions + Docker — typecheck, tests and consistent MongoDB in pipeline before merge.
  • AI-assisted workflow — Cursor, Claude, MCPs for speed on boilerplate; architecture and production code reviewed manually.

Challenges

  • Designing scheduling UX that office admins can trust and adjust quickly
  • Keeping mobile useful with intermittent connectivity and simple day-to-day flows
  • Maintaining security boundaries for medical/HR documents across roles and tenants
  • Shipping incrementally while working full-time as a paramedic — small, reviewable changes over big rewrites

Outcome

A live platform used for real operations: one place for planning, worker data and field access. The codebase is structured for a small team to extend — clear module boundaries, typed clients, and delivery habits (Git, CI, review) that match how I would work in a product team.

Code and live access are private. I can walk through architecture, screenshots and technical decisions in an interview or call.
